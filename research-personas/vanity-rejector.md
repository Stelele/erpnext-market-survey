# Vanity Rejector

**Persona archetype:** The founder who distinguishes ruthlessly between what founders care about (UI polish, API elegance, documentation beauty, code cleanliness) versus what customers actually pay for (solving the problem, reliability, results, not having to think about it). Treats founder vanity as the enemy of customer value.

## Lighthouse Quote

> "Nobody wakes up excited about your billing integration. They wake up excited about what they can do with their business." — Rob Walling

> "The best marketing is a product that actually works and a founder who genuinely cares." — Patrick McKenzie

> "The best product is the one that exists and works, not the one that doesn't exist but is theoretically better." — Sahil Lavingia

## Discovery Triggers

- Explicit discussions of features founders love but customers don't care about
- Ship now, iterate later as a guiding principle (perfectionism as enemy)
- Distinguishing between "would a customer pay for this?" and "is this technically impressive?"
- Prioritizing reliability and boring functionality over shiny new features
- Customer complaints about bugs or missing features that founders dismiss as "vanity issues"
- Willingness to ship ugly-but-functional over beautiful-but-nonexistent

## Validation Threshold

- Customer complaints are about missing functionality, not UI polish
- Shipping velocity is high (no feature takes more than a week)
- Customer retention correlates with problem-solving, not product aesthetics
- Time spent on "vanity" features is tracked and minimized

## Red Flags

- Spending weeks on UI polish before shipping to real customers
- Conflating technical elegance with customer value
- Delaying launch for documentation that customers will never read
- Obsessing over API design before proving the product is worth integrating
- Ignoring customer feedback because "they don't understand the vision"

## ERPNext Ecosystem Lens

Vanity Rejectors in the ERPNext ecosystem would:

- Ship ERPNext apps with functional but minimal UI (Frappe's default desk is fine)
- Focus ERPNext development on backend logic and data accuracy over frontend polish
- Ship ERPNext apps quickly to the Frappe App Directory without extensive documentation
- Prioritize ERPNext app reliability (correct calculations, data integrity) over beautiful charts
- Accept ERPNext's existing UX patterns rather than building custom frontends
- Target ERPNext features that customers have complained about for years (proven pain, not imagined elegance)

**High-value ERPNext vanity rejection:**
- ERPNext apps that solve existing pain points (no need for beautiful UI if it works)
- ERPNext integrations that "just work" over feature-complete integrations
- ERPNext reporting that has the right numbers over beautiful visualizations
- ERPNext migration tools that reliably work over tools with pretty UIs
